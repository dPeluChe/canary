# 2026-08 — origin

## Where canary came from

On 4 August 2026 a maintainer account compromise led to malicious versions
being published across 400+ npm packages in the keyv / cacheable family.
Public report: [Wiz Research](https://www.wiz.io/blog/keyv-and-cacheable-npm-supply-chain-attack).
Full IoC list: [wiz-sec-public/wiz-research-iocs](https://github.com/wiz-sec-public/wiz-research-iocs)
(`reports/keyv-packages.csv`, 443 packages).

The payload stole cloud credentials, SSH keys, AI-tool config files
(Claude / OpenAI / Cursor / Gemini), CI/CD variables and wallets — and
persisted by installing Claude Code hooks and modifying VS Code `tasks.json`.

An incident response was run by hand over a workspace of ~80 repositories.
The result was clean. What was interesting was **the procedure**, not the
finding: half of it had no tool behind it.

## What the manual investigation actually did

1. **Lockfile cross-check** — 317 lockfiles against the 443-package vendor
   list, matching name *and* version, across `package-lock.json`, `yarn.lock`,
   `pnpm-lock.yaml` and `bun.lockb`.
2. **Parser self-validation** — re-ran the match with the version filter
   removed, to prove the parser could see the affected family at all before
   trusting a negative result. It found the family at safe versions
   (`keyv@4.5.4` vs malicious `6.0.0`, and so on). **A negative from an
   unvalidated parser is worthless**, and this step is now a design
   requirement.
3. **CI window correlation** — every repo with workflows, cross-referenced
   against the window, then for the one repo that did run CI in it: how it
   installed (`npm ci`, strict from lockfile), what its lockfile contained
   (nothing from the affected family), and what secrets existed (none). Clean,
   with a reason.
4. **Persistence sweep** — VS Code `tasks.json`, Claude Code settings and
   hooks, global git hooks, all checked for both content and modification time.
5. **Artifact sweep** — C2 domain, IP, embedded intimidation string, dropped
   filenames, across the whole tree including installed `node_modules`.

## Failures worth keeping

**The zsh word-splitting bug.** The first CI sweep reported "zero runs in the
window" across 32 repos. It was wrong: the loop iterated a space-joined string
that zsh does not word-split, so the loop body never executed, and `2>/dev/null`
swallowed the evidence. Rerun with a proper array, it found 23 runs in one repo.

A scan that finds nothing and a scan that never ran look identical from the
outside. This is why `verdict.Status` has a first-class `Skipped` and why
`Report.Gaps` is mandatory.

**The `Math_Symbol.js` false positive.** The published indicator was a bare
filename that also names a legitimate Unicode data file shipped by
`regenerate-unicode-properties`. The real indicator was that filename inside
the compromised package. Hence `attack.Artifact.PathScope`.

## Decisions taken

| Decision | Reason |
|---|---|
| Separate project, not a feature of existing tooling | Security work needs its own release cadence and blast radius |
| Go, not Rust | OSV-Scalibr is an importable Go library; the whole security ecosystem is Go. See RESEARCH/LANGUAGE_DECISION.md |
| spark as reference only, no code extraction | Its dependency model has a fatal bug for this use case. See RESEARCH/SPARK_ANALYSIS.md |
| Read-only, no remediation flag, ever | A forensic tool that modifies destroys its evidence |
| Campaigns as data files | Vendor lists beat OSV advisories by days |
| Headless first, TUI as viewer | spark is 36% interface and awkward to run unattended |
| Layer 3 delegated to zizmor | 23 mature rules; competing is wasted effort |
| Isolated from all other tooling in the workspace | Explicit scope boundary |
| `watch` mode is in scope, but watches the **feed**, not the filesystem | The inventory changes slowly; the campaign list changes daily. Same engine, triggered by a new campaign instead of by a human. Install-time interception and live host monitoring stay out — different products, different risk profile |

## Not established

- **Reddit / community sentiment.** reddit.com was unreachable from the
  research environment and `site:` searches returned aggregators. Nothing in
  RESEARCH/ reflects community consensus — only repos, vendor blogs and docs.
- **Other developers' machines.** The manual investigation could inspect team
  repos but not teammates' laptops. That gap is inherent, and canary should
  state it rather than imply coverage it does not have.

## A fifth of the same species, in a sentence

A review found layer 4 telling a human the wrong reason.

`Material()` can be false for two reachable reasons — no malicious version was
resolved, or there was nothing reachable to steal — and they are **opposite
findings**. One message covered both, so a repo that genuinely had a malicious
version installed by CI in the window, but no secrets, was told *"no malicious
version resolved"*.

The escalation logic was right: without secrets there is nothing to raise. Only
the sentence was wrong. But in a forensic tool the sentence IS the product, and
this is the fifth time the defect has taken the same shape — something computed
correctly that reaches the human as something else.

The running checklist for anyone touching the report: **does the new branch,
field or message reach `Findings()`, `text()`, the exit code, and does it say
which case it is in?**

## The inventory, and a speedup that was not one

`canary scan -reuse` matches a newly published attack against the set already
resolved: **0.08s against 15.9s** for a full scan, over 322 repos and 33,047
unique package versions. The file is 2.6 MB because packages are stored once
and repos hold indices — a real tree resolves the same few thousand packages
across hundreds of repos.

### Where it is NOT written

TASK_TODO said `.canary/inventory.json`, which means inside the scanned tree.
That breaks invariant 1, and the read-only test written two entries ago would
have failed on it. It lives in canary's own data directory instead, keyed by a
hash of the tree so several coexist. `$CANARY_DATA_DIR` overrides it — which is
also how the tests stopped writing into the developer's home, something the
first implementation did until a real run showed ten stray files there.

### The first version was not faster

Measured before believing it: 13.3s against 15.9s. Barely anything.

`-reuse` was skipping only `deps.Extract` while still walking the whole tree
with `discover` and running layers 2, 3 and 4. **The extraction was never the
cost.** A cache that avoids the cheap half of the work is not a cache.

Rewritten so `-reuse` touches nothing at all — no walk, no sweep, no network —
and takes its repos from the inventory itself. 0.08s. Proven by a test that
**deletes the scanned tree** and asserts the reuse run still reports the
finding: it cannot be reading anything else.

That answer arrives with its own limits printed, because a fast answer that
implied a full sweep would be the worst kind of speedup:

    layers 2, 3 and 4 did NOT run: -reuse answers only whether a new attack
      touches the already-resolved package set
    matched a stored inventory built 2026-08-08: the tree was NOT re-read,
      so anything installed since is invisible

Past a week it also says the inventory is stale and to re-scan — a tree that
resolved clean then is not clean now.

## Running it for real, which found what the audits did not

A full scan of the author's workspace had never finished — killed at six
minutes with nothing printed. It now completes in **1:56** over 322 repos.

Measured before optimising, on a 43k-file subtree: the walk cost 0.77s and
adding every file read cost only 0.4s more. **The bottleneck was walking, not
reading**, which is not where the effort would have gone by intuition.
`filepath.WalkDir` is sequential, so directories now go to a worker pool as
they are discovered and one enormous `node_modules` no longer serialises the
sweep. 5.2x on the walk; the read path was already concurrent.

### The bug only a real tree could show

The report attributed `labs-canary/cmd/canary/scan_test.go` to the repo
`_code_` — the workspace root, which is itself a git repository. A bare prefix
match hands a finding inside a nested repo to its parent.

`discover` solved exactly this for lockfiles and says so in a comment —
"longest path first so nested repos claim their lockfiles before parents do" —
and layer 2 reimplemented the naive version. The finding pointed at a repo that
does not own the file, which for a forensic report is a wrong answer stated
confidently.

**No audit found it. Two review passes and 120 tests did not find it. Running
the binary on a real tree found it in one run.** That is the argument for
shipping something people can run.

### Output that survives 322 repos

180 identical CLEAN lines is a wall that buries the sections worth reading, so
past twenty repos CLEAN collapses to a count and `-v` restores the detail.
SKIPPED collapses too but **keeps every reason** — what was not checked, and
why, is the half of the report that is easiest to lose and worst to lose. The
sweep now also reports how many files it walked and read, because that is
coverage, not diagnostics.

### Resolved.Direct, deleted

scalibr cannot fill it, computing it needs the per-format manifest parser
CLAUDE.md forbids, and DATA_MODEL forbids filtering on it. A field that cannot
be filled honestly and cannot be used to decide is a trap for whoever reads it
next. The reasoning now lives where the field was.

## Invariant 1, proven instead of asserted

The audit's list of things it could not check had this at the top: read-only was
read for, never demonstrated.

A syscall trace was the obvious answer and is the wrong one. On macOS it needs
SIP disabled or root, so it becomes a manual ritual nobody repeats — and it
proves **one run on one machine**. Hashing the whole tree before and after
proves every run, on every platform, in CI, and keeps proving it when someone
later adds a layer that writes.

The fixture has something for each layer to find — a malicious lockfile, a C2
domain on disk, `.claude/hooks`, `tasks.json`, a service worker, git hooks, a
`pull_request_target` workflow, and a payload inside `node_modules` — because a
layer that finds nothing also writes nothing and would prove less. Path, mode,
mtime and content hash are compared, so a create, a delete, an edit and a touch
all fail it. The error paths get their own test: an unreadable directory, a
lockfile that does not parse.

Verified by planting `os.WriteFile` in the scan path. It failed with
`CREATED .canary-cache` **and** `MODIFIED .` — the directory's own mtime moved,
which is the change a content-only check would have missed.

### And the excuse that did not survive checking

`canary update` fetched shai-hulud but not DataDog, and the reason given was
that DataDog is a git clone like OpenSSF. That was wrong: its manifests are
1.6 MB and 50 KB over plain HTTP. Two GETs, not a clone. Now wired, and
`update` pulls **51,502 entries across three sources**.

The lesson is small and worth keeping: a justification invented from the shape
of a neighbouring case is not a verified one. OpenSSF really is a clone;
DataDog was assumed to be by association.

## canary update, and the first source that is not a manual CSV

`canary update` fetches the redistributable lists. Only lists with a licence
that permits it: shai-hulud-detect is MIT, and the vendor incident CSVs stay
manual through `canary import` because they carry no licence at all.

Three properties worth keeping:

- **Download to a temporary file, parse it, and only then replace the cache.**
  A truncated download overwriting a good list would shrink the set canary
  matches against without saying so.
- **A source that failed to refresh is reported and exits non-zero.** The
  cached copy may be months old and will still be used.
- **canary writes only into its own data directory.** That is not a breach of
  the read-only invariant, which is about what canary INSPECTS — and refusing
  to write anywhere near a scanned tree is what keeps it literal.

### The number that needed explaining

The list has 5,699 `name:version` lines and loads as **2,364 entries**. That
gap is the merge working: `add` keys by package and widens the version list, so
`autotel-subscribers` with 28 malicious versions across 28 lines becomes one
entry carrying all 28. Verified against the file rather than assumed, because a
loader that quietly dropped 3,335 lines would look exactly the same from here.

### Staleness is what buys explicit refresh

`canary attacks -corpus` prints when each source was last written, and says
STALE past a week. That is the whole argument for keeping refresh out of the
read path: a list nobody updated in months reports clean just as confidently as
a current one, so its age has to travel with it.

Scoped npm names made the parse non-obvious — `@scope/name:1.2.3` has two
colons and only the last separates the version. Splitting on the first would
have produced `@scope` at version `name:1.2.3`, an entry matching nothing while
the list looked fully loaded. Pinned by a test.

## Load-time drops: four ways a vendor list and a lockfile disagree

The audit's own "not covered" list put `attack`, `corpus` and `datadir` first,
on the grounds that a version lost at load time is the same clean-that-lies as
the three defects before it. Probing found four, none of which raised an error:

| A vendor list says | A lockfile says | Matched? |
|---|---|---|
| `v6.0.0` | `6.0.0` | no |
| `6.0.0` | `6.0.0+build.7` | no |
| `Keyv` | `keyv` | no |
| `">=1.0.0, <2.0.0"` | anything | no — the CSV importer split the range on its comma into two entries that match nothing |

Each one produced a CLEAN verdict with the attack loaded.

The fixes are deliberately narrow. `NormalizeVersion` strips a leading `v` and
build metadata — semver says build metadata is not part of precedence — and
touches nothing else; a prerelease is still not its release. `NormalizeName`
folds **only** where the registry publishes a rule: npm lowercases, PyPI
normalizes per PEP 503. Go module paths are left verbatim, because folding them
would invent matches rather than find them.

Ranges are **refused**, not parsed. Resolving them is OSV's job, and the silent
alternative was an attack file that looks fully loaded and matches nothing.

### And the same species one more time, caught by the end-to-end

Unit tests for the normalization passed, and the scan still reported CLEAN.

`deps.Match` builds a name index for speed and keyed it on the **raw** name, so
the lookup missed before `Matches` — the comparison the index exists to
accelerate — ever ran. A fix that never reaches the thing that decides: the
fourth instance of the pattern in this file, and the first caught by running
the binary rather than the test.

The lesson to carry: **a lookup that fronts a comparison must fold exactly as
the comparison folds**, and a unit test on the comparison alone cannot see it.

## Invariant 3, finally proven for all five formats

`deps.Supported` advertised five lockfile kinds and exactly one had ever been
proven transitively complete. The other four were a promise with no evidence —
and an extractor that quietly returned only declared dependencies for yarn or
pnpm would reproduce the defect that made the reference project useless, with
every negative from it worthless.

Each format now has a fixture where `package.json` declares 8 and the lockfile
resolves 301, with `keyv@6.0.0` present ONLY as a transitive:

| kind | resolved | declared |
|---|---|---|
| package-lock.json | 301 | 8 |
| npm-shrinkwrap.json | 301 | 8 |
| yarn.lock | 301 | 8 |
| pnpm-lock.yaml | 301 | 8 |
| bun.lock | 301 | 8 |

**All five go red when extraction is replaced with spark's manifest-based
model** — 8 resolved against 8 declared, and keyv gone.

The fixtures were built by reading scalibr's own testdata rather than guessing
the formats, and probed empirically before being fixed as a test. The three new
formats needed a different shape than package-lock: yarn.lock is a flat list,
pnpm separates `dependencies` from `packages`, and bun.lock keys a JSON map to
`[spec, {}, hash]` tuples. None of them carries package-lock's root entry, so
the comparison has to be against the manifest, not against the lockfile's own
structure.

A second test pins that `Supported` and `Extract` agree: every advertised kind
actually parses, and `bun.lockb` — binary, found by discover, readable by
nobody — is correctly refused. Claiming support for a file nobody can read
turns an unread lockfile into a clean answer.

## A second review, and the same species again

A second adversarial pass found one real bug, and it was mine for the third
time in the same shape: `Report.Findings()` ignored `HomeFindings`.

Persistence in `$HOME` is stored apart from `Repos` — deliberately, since it
belongs to the machine rather than a project — and the exit code only looked at
`Repos`. A C2 domain in `~/.zshrc` printed under DEVELOPER MACHINE while the
process exited **0**. The report said one thing and the contract CI branches on
said another.

Three times now the defect has been the same: **evidence that exists, is
computed, and does not reach the thing that decides.** First artifacts computed
and never printed, then a skip outranking a layer-2 hit, now a report field
outside the exit-code check. The shape to watch for is a new field or branch
added on one side of the report without wiring it into the other.

### The tests that should have existed

Both `cmd/canary` and `verdict` had none, which is why every one of these
survived. The internal packages were all correct in isolation; the assembly
dropped evidence on the floor. Seven tests now pin the orchestration — which
status wins, what reaches the text report, the exit-code contract, orphan
coverage — and seven more pin the output contract.

Each was checked by reverting the fix and confirming it goes red. A test only
ever seen passing has not been shown to detect anything.

### One claim declined

The review also flagged `appendUnique` as quadratic on trees with hundreds of
malicious packages. It is not: `Finding.Attacks` is bounded by the number of
loaded attack files, not by the number of findings, so hundreds of malicious
packages are hundreds of small lists. Reported back rather than changed.

## The adversarial audit, and the bug it found in my own fix

Five review lenses over the whole codebase in parallel — correctness, product
invariants, false negatives, canary's own security against hostile trees, and
reuse — then every finding handed to a separate agent whose only job was to
**refute** it, told to default to refuted when unconvinced.

29 raw findings, 8 sent to refutation, **8 survived, 0 refuted**. Several
refuters built the binary and reproduced the defect end to end with a control.

**The deduplication was the weak part, not the finders.** Keying on filename
plus the first 60 characters of the claim did not collapse the same defect
described in different words by different lenses: findings 1, 4 and 8 were one
bug, 2 and 6 another, 3 and 7 a third. Four real defects, reported as eight.
A future audit should dedupe on the code location and the mechanism, not on
prose.

### The one that matters

`depsSkipped` outranked layer-2 evidence. A repo with a dropped payload on disk
and no lockfile was stamped `Skipped`, its artifact never printed, and the
process exited 0.

```
before:  SKIPPED — 1 repo(s) NOT checked / repoA  no lockfiles      exit 0
after:   CONFIRMED — repoA / src/app.js:1 — domain "npm-cache-evil.com"  exit 1
```

**This was introduced by the previous entry's own fix.** Wiring zizmor exposed
that a repo with unreadable lockfiles returned early, so layers 3 and 4 were
moved after the skip — and layer 2 was left behind it. A partial fix to a
skip-too-early bug reintroduced the same bug for a different layer.

It is the exact failure this project exists to prevent, inside this project: a
compromised repository reported as unchecked-and-uninteresting, with the
evidence sitting in memory and withheld from the report.

### The other three

- **Orphan lockfiles were discovered and never scanned.** `discover` reports
  lockfiles outside any git repo on purpose — unpacked tarballs, vendored app
  directories, un-repo'd checkouts, exactly where an incident tree has
  stragglers — and `scan` iterated only `inv.Repos`. A malicious version there
  was neither matched nor declared missing, while the run still asserted the
  family was absent from the whole tree.
- **Sweep hits under no repo path were dropped**, with a comment claiming the
  opposite. Both are now one `(outside any repo)` entry.
- **Layer 4 read only the first page of runs.** A busy repo has more than 100
  in a window. Now paginated, with a declared ceiling — a bound is necessary,
  a silent one would be the same defect in a new place.

### What the audit says it did NOT cover

Worth more than the findings. `attack`, `corpus` and `datadir` were treated as
trustworthy inputs and not read in depth. **Invariant 3 was never verified at
its source** — nobody checked that `deps.Extract` actually resolves transitives
for each of the five formats it advertises, which is the specific bug that
killed the reference project. Invariant 1 was read for, not proven; nobody
traced syscalls.

And the structural finding that explains why three of four defects shared one
file: **`cmd/canary` has no tests at all.** Every decision about which status
wins, what gets printed and which exit code is returned is untested.

## Layer 3: delegated, and verified against the real binary

The last layer, and the only one canary does not implement. zizmor has 23
audits and is maintained; competing would age badly.

**The schema was read off the real binary, not guessed.** zizmor was installed
specifically to see what `--format json` actually emits — `ident`, `desc`,
`url`, `determinations.severity`, and a `locations[].concrete.location.
start_point.row` that is **0-indexed**, so a report that forwarded it verbatim
would send a human to the wrong line. Verified against 1.29.0.

Two behaviours that matter more than the parsing:

- **zizmor exits 14 when it finds something.** Exit status alone cannot tell
  findings from failure, so stdout is the signal and a parse failure is an
  error — an empty result would read as clean.
- **Its findings are Suspected, never Confirmed.** zizmor answers "could this
  workflow be abused", not "were you attacked". It must never escalate a repo
  the forensic layers found clean, and the absent case must never read as a
  pass: no zizmor installed prints a gap saying the workflows were not audited.

### A skip that was swallowing repos

Wiring this exposed a real bug in `scan`: a repo whose lockfiles could not be
read returned `Skipped` and `continue`d **before layers 3 and 4 ran**. A repo
with no lockfiles but a `pull_request_target` workflow checking out untrusted
code was reported as "not checked" with nothing else said. Layer 1 having
nothing to read is not the end of a repo.

## Layer 4: CI inside the window

The last differentiator, and the one no surveyed tool does. A laptop can be
verified clean while a runner installed the same dependency tree and
exfiltrated repository secrets, leaving nothing behind locally.

**The rule the layer exists to enforce is a restraint, not a detection.** A run
inside the window is not a finding. Neither are secrets. `Material` requires
three signals at once: a run that actually **installed dependencies**, secrets
**reachable** from it, and a malicious version **actually resolved** by layer 1.
Anything less is recorded and deliberately not escalated — the common outcome is
a documented negative, and reporting runs alone produces alarm without
information. Six cases pin that table in the tests.

`npm ci` counts as an install. Installing strictly from a lockfile is safer than
`npm install`, but it still executes whatever the lockfile pins — which is the
entire premise of layer 1.

Distinctions that took care:

- **Secrets unlistable is not secrets absent.** `SecretsUnknown` is its own
  field, and it counts as exposure in `Material`. Conflating the two would
  understate risk exactly where the token is weakest.
- **Layer 4 is opt-in (`-ci`)** because it needs a token and network, and every
  other layer works offline. Not running it records its own gap, since "we did
  not look at CI" must never read as "CI was clean".
- **Rate limiting is a distinct error**, so the report can say which repos were
  never checked rather than counting them clean.

Tests use a local `httptest` server — the same rule the filesystem layers
follow, never touching the real thing. The live path was then verified once
against the real API with a token: the query succeeds and returns zero runs for
a repo with no workflows, which is the correct empty answer rather than an
error.

## Layer 2, second half: persistence

The differentiator is finished. Two families, reported apart because they mean
different things: **developer machine** (Claude Code settings and hooks, VS Code
`tasks.json`, git hooks, shell profiles) and **deploy surface** (service worker,
served HTML, CSP config, `.well-known/`).

These are known addresses, so they are stat-ed directly rather than searched. A
tree walk would cost what the artifact sweep costs and find nothing more.

### Two strengths of evidence, kept apart

The line that took the most thought. A location carrying a known indicator is
**Confirmed**. A location that merely moved inside the window is **Suspected** —
because `~/.zshrc` edited this week is completely ordinary, and a tool that
called that a compromise would be crying wolf on every developer alive. The
report says "no known indicator: verify by hand" and means it.

The inverse holds too: an indicator in a file with a six-month-old mtime is
still a finding, and the wording must not imply it happened in the window.

**`.git/hooks/*.sample` are excluded.** Git ships nine of them inert; flagging
them would bury the one hook that actually runs under nine that never do.

### Untouched is evidence

`PersistenceUntouched` counts locations inspected and found old and clean. That
number is what lets a clean verdict state what it checked — on this machine, 13
locations inspected, 12 untouched. Without it "no persistence findings" would be
indistinguishable from "no persistence check".

### $HOME is outside the tree

Reading `$HOME` is what finds agent-hook persistence, and it is also going
somewhere the user did not ask about when they named a project directory. So a
run that goes there **says so as a gap**, names how many locations it inspected,
and `-home=false` turns it off — which records its own gap, because declining to
look at the place the 2026 attacks persisted is itself a coverage hole.

Home findings are reported in their own section rather than attributed to a
repo: persistence in `$HOME` belongs to the machine, and pinning it on whichever
project happened to be scanned would be wrong in both directions.

### A duplicate the sweep and the check both found

A service worker is walked by the artifact sweep and inspected as a deploy
target, so the same hit arrived twice. `Result.Merge` now dedupes by path,
artifact and line, keeping the persistence copy — it carries the family and the
note explaining why that location matters.

## Layer 2, first half: the artifact sweep

`PathScope` finally works, and it needed a glob matcher written by hand:
**stdlib `filepath.Match` does not implement `**`**, so
`**/node_modules/keyv/**` would never have matched a nested path. This is not a
detail — PathScope is the only thing standing between a filename indicator and
the `Math_Symbol.js` false positive that motivated the field. The pair is now
pinned by a test: the same filename under `node_modules/keyv/` is a finding,
under `regenerate-unicode-properties/` it is not. Verified end to end on a tree
carrying both — two on disk, one reported.

Content and mtime are reported separately, as the model always said they should
be. A file carrying the C2 domain with a six-month-old mtime is still a finding
but not one that happened in the window, and with no window given nothing is
claimed to be inside one — reporting everything as in-window would be the
alarming answer rather than the correct one.

### What it costs, measured

The sweep opts back into `node_modules` by design, and that is expensive.
Measured: **20,686 files in 0.62s, about 33k files/second** with bounded
concurrency (the walk stays sequential, the reads fan out to NumCPU workers).

On the author's full workspace it does not finish in minutes — but neither does
`find` on the same tree, which is the honest framing: the tree is of the order
of ten million files, not the sweep being slow. `-sweep=false` runs a
dependency-only pass, and choosing it records a gap saying the tree was not
searched.

The cheapest optimisation is not in canary: **a content artifact with a
PathScope costs nothing outside its scope**, because the file is never opened.
An unscoped domain indicator means reading every text file in the tree. That
gives PathScope a second reason to exist beyond false positives, and there is a
test asserting only the scoped file gets read.

## Two proposals evaluated, one of them productive

**cvelistV5** is out. OSV already carries CVE data mapped to packages —
`lodash@4.17.15` returns six advisories, all six with CVE aliases. The raw list
is 2.4 GB, has no LICENSE file, and its records do not identify the package:
`CVE-2024-21538` lists `vendor: n/a, product: cross-spawn, packageName: null`.
Turning that into `npm/cross-spawn` is fuzzy matching, and that mapping is
precisely the work GHSA and OSV maintain. Consuming it raw would be rebuilding
their job badly. CVE also answers a different question than canary asks — has a
vulnerability, versus is malicious on purpose.

**web-check** is out as a tool and productive as a question. Thirty of its
thirty-five checks need a live domain; canary never touches infrastructure. But
the proposal came with an argument worth taking seriously — that a repository
can carry web-surface risk too — and that argument found a genuine hole.

Layer 2's persistence targets were all developer-machine: Claude Code hooks,
VS Code `tasks.json`, shell profiles, git hooks. **Nothing covered files
committed in the repo that ship to users.** A postinstall payload can write into
`public/`, and what it writes is served verbatim on the next deploy.
`robots.txt` — the file that prompted the question — is the least interesting
member of that family. A service worker is the most: it persists in the
visitor's browser and survives a clean redeploy until someone unregisters it.
Then injected script tags in served HTML, and CSP weakened in `_headers`,
`netlify.toml` or `vercel.json`.

Added to layer 2. It stays repo-local, read-only and offline, which is exactly
why it belongs here and the tool that inspired it does not.

The pattern worth keeping: a proposal can be wrong about the tool and right
about the risk. Declining the tool without reading the argument would have lost
the finding.

## The cross: canary answers its own question

`deps.Match` crosses the resolved set against loaded attacks and corpus, and
`canary scan` wires discover → extract → match → verdict. That is the manual
procedure from the top of this file, automated end to end.

Run against the real workspace — 322 repos, 486 lockfiles, 8.2 seconds, matched
against the 446-package Wiz list:

```
CLEAN — 180 repo(s)
SKIPPED — 142 repo(s) NOT checked
```

**125 of the clean repos report the affected family present at safe versions.**
That number is the point. `deps.MatchIgnoringVersions` re-runs the cross with
the version test removed, so a clean result comes with proof the extractor can
see the family at all — the manual step that made the original "no malicious
versions" mean something. A run that never matched anything at any version now
says so as a gap: that negative is unproven, and unproven is not clean.

Findings carry provenance per package — which attack file, which corpus source
— because one vendor list saying it and three sources agreeing are different
claims. Matching goes through a name index: 250k resolved packages against 448
attack entries benchmarks at 9.4ms, where the naive pair loop would dominate a
scan.

The gaps are the other half of the output. A scan today prints that layers 2, 3
and 4 are not implemented, that OSV was not queried, and every lockfile kind it
could not read — `Cargo.lock`, `Gemfile.lock`, `bun.lockb`, `composer.lock`.
142 repos come back SKIPPED rather than folded into the clean count. A tool
that reported 322 clean here would be lying by omission.

## Corpus sources, and a review that had to check the claims

A cumulative-corpus layer arrived from another agent. The central design call
was right and is kept: **a corpus is not an attack file.** An attack is one
compromise with a forensic window that layers 2 and 4 key off; DataDog's
dataset spans years and many unrelated incidents. Forcing it into `Attack`
would have invented a meaningless `Started` and polluted the window-based
layers. It is a layer-1 lookup source instead.

Review found the rest did not hold, and every defect was the same species —
something that looks like coverage and is not:

- **`LoadDataDog` failed completely against the real dataset.** The subdir map
  said `ide-extensions`; upstream publishes `ide_extensions`. Since an unmapped
  subdir is deliberately fatal, one separator killed the whole load. The tests
  passed because the fixture used only `npm` and `pypi` — the fixture agreed
  with the wrong implementation, which is why layer 1 was checked against real
  lockfiles and not only its own fixture. There is now a test pinning the four
  names upstream actually publishes.
- **The exit codes were inverted.** A malicious hit returned 0 and a miss
  returned 2, so `canary corpus <dir> <pkg> && echo ok` printed ok exactly when
  the package was malicious. Now a hit is a finding (1) and a miss is clean (0),
  with wording that says absence from a list is not evidence of safety.
- **Provenance was per corpus, not per entry** — every entry claimed every
  source. Correct today only because there is one source. Entries now carry the
  sources that actually flagged them.
- **Merging duplicates could narrow coverage**: a source listing three versions
  overwrote one that said "all versions". Merging now only ever widens.
- **Matching was reimplemented** rather than reusing `attack.Package`, so the
  corpus compared ecosystems case-sensitively while attack files did not. Layer
  1 composing both would have answered differently depending on which list
  found the package first. `corpus.Entry` now embeds `attack.Package`, and a
  test asserts the two cannot disagree.

### Folded under attacks, and one resolver for both

`canary corpus` became `canary attacks -corpus`. A corpus answers the same
question attack files answer — "is this malicious?" — so it is a source, not a
third top-level noun. The command surface stays at two words and `-corpus`
returns before any attack file is touched, so asking for a corpus never fails
on a missing attack directory.

Directory resolution was then duplicated: `attack.ResolveDir` and
`corpus.ResolveDir` were identical but for three strings. Both now wrap
`internal/datadir`, whose test pins the case that sharing actually risks — two
data sets resolving to the same default because a caller was wired to the wrong
subdirectory. Public APIs and printed output are unchanged.

That is the second time the same rule caught something in this layer, after a
duplicated `dedupe`. Worth noticing as a pattern rather than fixing twice in
silence: parallel packages invite copy-paste, and the copy is always right
until one side changes.

### The licensing near-miss

`lxyeternal/pypi_malregistry` was documented as **CC0**. It has no LICENSE file
and its README states no licence — default copyright applies, exactly like the
Wiz IoC repository this project already refuses to vendor for that reason.
Acting on the CC0 label would have meant redistributing someone's work without
permission.

Counts were wrong too: DataDog was written up as 28,623 packages; counted from
the manifests it is 47,306 npm plus 1,833 PyPI. And a **0-star** fork was listed
as a cross-reference source, which this very document's "check the numbers
first" rule exists to prevent.

The lesson is not that the work was careless — the design judgement in it was
better than the details. It is that **a claim about a licence or a count is a
fact, and facts get verified before they enter a doc**, because a wrong licence
in a security tool's documentation is the kind of error that gets acted on.

## Command surface: nothing longer than two words

Adopted as a hard rule, from a plain observation about use: if scanning or
updating takes three or four words, the CLI is working against the person
using it.

```
canary discover <path>       canary attacks           canary import -csv <f>
canary scan <path>           canary attacks <id>      canary update
canary view [report.json]    canary watch
```

That killed `list` and `show`, which were noise: `canary attacks` already
means "show me the attacks", and a bare positional argument is obviously an
id. `import` moved to the top level for the same reason. It also removed the
subcommand-after-flag parsing bug entirely — there is no subcommand left to
misplace.

Renamed while it was free. Nobody outside this repo uses these yet.

### Multi-source attacks, with provenance

`attacks` becomes the centre. Not one source but several, because no single
list has everything and the gap between them is measured in days:

| Source | What it gives | Licence |
|---|---|---|
| OSV.dev `querybatch` | `MAL-` + CVE, cross-ecosystem, authoritative | free |
| OpenSSF malicious-packages | the same data raw and clonable, OSV format | Apache |
| Cobenian/shai-hulud-detect | 5,752 `name:version` across several campaigns | **MIT** |
| Wiz / Aikido / StepSecurity | per-incident, first out | **none** — fetch, never vendor |

All three free sources were re-verified reachable before committing to this.
shai-hulud-detect in particular is **not** the abandoned single-incident
scanner TOOLING_LANDSCAPE implies: MIT, actively pushed, and its list is a
plain `name:version` file. That doc should be corrected.

Two requirements come with it, both from existing invariants:

1. **Provenance per entry** — which source called this version malicious. A
   vendor rumour and an OSV confirmation must not read the same.
2. **Sources consulted, printed.** DATA_MODEL says absence from both lists is
   not evidence of safety. With N sources it becomes absence from *the ones we
   could reach*, and an unreachable source is a gap, not a silence.

### Updating stays explicit

Rejected auto-refresh on any `attacks` invocation. The worry behind it is
right — a stale list yields a clean verdict silently, which is the failure this
project is shaped around — but a network call as a side effect of a read
command costs reproducibility, which forensics cannot spend: you must be able
to say "I scanned against exactly this list". It also breaks offline and
air-gapped use, at the moment you most need the tool.

Same protection, none of the cost: **staleness is shown loudly, refreshing is
`canary update`.** `canary attacks` prints the age of every source.

### TUI scope

Two screens: finished reports, and a browser for the attack catalogue — 446
packages is an unreadable terminal dump. Still a viewer only, per invariant 7.
If the TUI drove scans there would be two paths producing a verdict and the
interactive one would be the untested one.

## Layer 1: the transitive test, and the end of the stdlib-only build

The rule was that the first test in this layer proves transitive completeness
and that nothing gets built on top until it passes. It was written first,
failed first, and now passes.

The fixture reproduces the shape measured during the incident: 26 packages
declared in `package.json`, 790 resolved in the lockfile, 80 of them nested,
plus `keyv@6.0.0` planted nested and absent from the manifest — exactly where
the real one was. Extraction returns 791.

**The test was then verified to catch the actual bug**, not just the stub.
Replacing extraction with spark's model — keep only what the manifest declares
— turned it red with the number that matters:

```
resolved 26 packages, want 791 — a manifest-based scanner returns 26
keyv@6.0.0 is nested in the lockfile and was not resolved — this is the spark bug
```

A test that has only ever been seen failing against `panic("not implemented")`
has not been shown to detect anything. This is the third time that principle
has earned its place in this file.

Confirmed against real lockfiles too, since a synthetic fixture can agree with
a wrong implementation:

| repo | manifest declares | resolved |
|---|---|---|
| labs-ligamx | 26 (11 + 15 dev) | 288 |
| labs-polizahoy | 68 (36 + 32 dev) | 956 |

The first row is the spark case verbatim: 26 declared, 288 present.

### What this cost

`osv-scalibr` v0.4.5 brings **one direct dependency and 156 indirect ones**,
and the binary goes from under 2 MB to 3.1 MB.

That ends "builds with zero network" for a fresh clone. It is worth naming
plainly because the small-dependency-surface argument is the one that decided
JSON over YAML for attack files, and it is now weaker. The trade is still
right — hand-writing lockfile parsers is precisely the defect that made the
reference project useless, and scalibr is the library osv-scanner itself is
built on — but it is a trade, not a free win. A build from a warm module cache
still works offline.

### Not done, deliberately

- **`Resolved.Direct` is not populated.** scalibr reports dependency *groups*
  (dev, optional), not whether the manifest declared a package. It stays false
  rather than guessed. Per DATA_MODEL it may never be used to filter anyway.
- **Only the npm family is wired** — package-lock, npm-shrinkwrap, yarn, pnpm,
  bun.lock. Every other lockfile kind discover finds returns an explicit
  "unsupported" error rather than an empty result, so it can surface as a gap
  instead of a clean answer.

## The CSV converter is Go, not shell

`scripts/fetch-attack.sh` was supposed to grow a converter. It did not: the
conversion lives in `canary attacks import` instead.

The real Wiz list is 446 packages, and **358 of those rows quote their version
list** — `"1.4.2, 1.4.3, 1.4.4"`. The commas inside the quotes are data. A
shell loop splitting on commas mangles four rows out of five and says nothing,
which is the same class of bug as the zsh word-splitting failure above: wrong
output that looks like output. `encoding/csv` is stdlib and gets it right.

Two decisions inside it:

- **Output goes to stdout**, never to a file. Redirect it yourself. canary's
  first invariant is that it does not write, and a converter that creates files
  makes that invariant something to argue about instead of something to check.
- **A row with no versions is an error**, not an empty list. Empty versions mean
  *every* version of that package matches — a serious claim, and not one a
  converter should make on a vendor's behalf out of a blank cell.

Columns are found by header name rather than position, because vendors publish
the same two columns in different orders. Conversion output is run through
`validate()` before it is printed, so a successful import cannot produce a file
that `Load` would later reject.

## Renamed: campaign → attack

The word did not survive contact with its first reader, who took "campaign" to
mean *our* review cycle — an iteration the team runs — rather than the
attacker's. That reading is reasonable and it inverts the entire model: the
file describes what was done TO us, and canary runs scans against it.

`campaign` is correct threat-intel vocabulary and it is what Wiz and Socket
publish under. But canary's user is a developer with a tree of repos, not a
threat analyst, and the first such developer to read the word misread it.

Now `attacks/keyv-2026-08.json`, `canary attacks list`, `--attack <id>`,
`internal/attack`. Plural in the command position on purpose: `canary attack
list` sits beside the verbs `discover` and `scan` and reads as an order to
attack something, which is a bad look for a read-only forensic tool.

Rejected: `advisory` collides with the OSV `MAL-` advisories canary
deliberately contrasts local data against; `ioc` is already layer 2; `incident`
is precise but doubles as *our* incident-response event, the same ambiguity in
a new coat.

Done while the package had two files and nothing depended on it. After layer 1
lands it would have been expensive.

**Sections written before this one use the old word.** The journal is
append-only, so the narrative stands as written; only code identifiers and
paths were repointed so they still resolve.

## Campaign format — decided JSON

The scaffold left YAML vs JSON open. Decided **JSON, schema 1**, one campaign
per file, loaded from a directory.

The deciding argument was not readability. It was that a YAML library is the
only dependency that would cost canary its "builds with zero network"
property, and that the canonical upstream feed — OpenSSF `malicious-packages` —
is OSV format, which is JSON already. Campaign files are generated from vendor
lists at a size nobody hand-writes: 443 packages, out of a CSV. Full rationale
in ARCHITECTURE/DATA_MODEL.md.

JSON's one real cost is comments. `note` is therefore a schema field on the
campaign and on every artifact, so the reason an indicator exists is data and
reaches the report instead of dying in a `#` line.

`attack.Load` is deliberately all-or-nothing: one malformed file fails the
call, an empty directory returns `ErrNoAttacks`, unknown keys are rejected.
All three are the same failure wearing different clothes — a campaign set that
is quietly smaller than it looks, producing a clean verdict nobody should
trust. It is the zsh word-splitting bug above, at the data layer.

Two rules are enforced rather than documented:

- `kind: filename` without a `pathScope` is refused. That is `Math_Symbol.js`,
  turned from a lesson into a load error.
- Omitting `versions` means *every* version of the package matches. A hijacked
  or typosquatted package has no safe version, and layer 1's self-validation
  mode needs the same shape.

## Process: flowkit adopted, product isolation intact

Hooks, lint gates and the PR ritual now come from the shared flowkit layer.
This does **not** breach the scope boundary: the coupling is to the dev
process, not to canary's product surface. `go.mod` is still stdlib-only and
the binary depends on nothing in the workspace. If that ever stops being true,
the boundary rule wins.

No repo-local `.gitleaks.toml`. canary mints no token format of its own, so
central coverage applies, and a local file would *replace* the central config
rather than extend it. Worth remembering for later: campaign data files carry
C2 domains and high-entropy malware indicators **by design**. If the
generic-high-entropy rule ever fires on one, the fix is an allowlist path for
the campaign directory, not a local config that quietly drops the other rules.

Switched to team mode afterwards, on the assumption that someone else may clone
this repo. `lefthook.yml` is committed as the shared base and the machine-local
overlay (`lefthook-local.yml`) and the personal agent import (`CLAUDE.local.md`)
stay out of git. The committed `CLAUDE.md` no longer carries a `~/.agents/...`
path, which would have been a broken import for anyone but this machine.

**A failure worth keeping, found doing it:** deleting `lefthook.yml` and leaving
only `lefthook-local.yml` looks equivalent and is not. Lefthook merges an
overlay onto a base; with no base it resolves **zero** jobs, and all six central
secret rules go from "blocked" to "unseen" — the hooks appear installed and
scan nothing. `flowkit hooks --verify` catches it because it plants a real
secret per rule instead of checking that files exist. Same lesson as the whole
project: a check that has never been observed failing has not been shown to
work.

The `lint` gate folds `gofmt` into `go vet`, because `gofmt -l` exits 0 even
when it lists unformatted files — used raw it is a false green. It is piped
through `(! grep .)` and was verified in both directions with a planted
misformat and a planted vet error. Same principle as the parser
self-validation above: a check that has never been seen to fail has not been
shown to work.
